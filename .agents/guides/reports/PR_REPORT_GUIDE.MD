# 📋 Руководство по составлению отчёта для Pull Request

Этот документ описывает стандарт оформления Pull Request для проекта **платформы отслеживания прогресса задач представителей избирателей** (стек: TypeScript, NestJS, Prisma, PostgreSQL, Vite, React).

---

## Структура PR-отчёта

```
## Тип
## Описание
## Ссылки на YouGile
## Скриншоты изменений
## Дополнительно
```

> **Тип**, **Описание**, **Ссылки на YouGile** и **Скриншоты** — обязательные разделы.
> **Дополнительно** — опциональный, добавляется по необходимости.

---

## 1. Тип

Укажите один или несколько типов изменений.

```markdown
## Тип:
- 🚀 Feature
```

| Эмодзи | Тип | Когда использовать |
|--------|-----|--------------------|
| 🚀 | Feature | Новая функциональность |
| 🔄 | Refactoring | Переработка кода без изменения поведения |
| 🐛 | Bug Fix | Исправление ошибки |
| 🎨 | UI/UX | Изменения интерфейса без бизнес-логики |
| 🗄️ | Database | Миграции, изменения схемы Prisma |
| 📝 | Docs | Документация, Swagger, README |
| ⚙️ | Config | Конфигурация окружения, CI/CD |
| ♻️ | Hotfix | Срочное исправление на продакшене |

> Если PR охватывает несколько типов — перечислите все.

---

## 2. Описание

**Количество пунктов строго равно количеству задач в YouGile.**
Один пункт = одна задача. Всё, что сделано в рамках одной задачи, ужимается в одну строку.

```markdown
## Описание
- [x] Краткое описание задачи 1.
- [x] Краткое описание задачи 2.
```

### Как формулировать пункт

Пишите в прошедшем времени: *«Добавлен»*, *«Реализован»*, *«Переработан»*.
Если задача затронула несколько слоёв (backend + frontend) — опишите в одной строке через «и» или точку с запятой.

> **Важно:** используйте только те термины, которые реально применяются в проекте. Не нужно вводить понятия из чужих технических культур — если в проекте нет «feature flags», «saga», «circuit breaker» и т.п., не стоит их упоминать. Описывайте то, что есть: модули, компоненты, эндпоинты, модели, страницы.

**Хорошо:**
```markdown
- [x] Создан endpoint `GET /api/v1/tasks/district` и добавлен фильтр по округу на странице задач.
- [x] Реализован баланс пользователя: модель в БД, эндпоинты, отображение в шапке и карточке.
- [x] Поле округа при регистрации переработано из текстового ввода в выпадающий список.
```

**Плохо:**
```markdown
- [x] Улучшен UI.                    ← слишком размыто
- [x] Добавлен endpoint.             ← нет деталей
- [x] Сделана миграция, добавлен сервис, добавлен контроллер и переделан компонент.  ← надо ужать в одну задачу
```

### Подсказки по формулировкам

**Backend (NestJS / Prisma / PostgreSQL):** указывайте метод и путь эндпоинта, называйте модели Prisma.

```markdown
- [x] Добавлен `GET /api/v1/tasks/district?name=<district>` для фильтрации задач по округу.
- [x] Добавлена модель `Transaction` (Prisma) и эндпоинты для работы с балансом.
```

**Frontend (Vite / React):** называйте компонент или страницу, описывайте видимый результат.

```markdown
- [x] Реализован компонент `DistrictBlock` с данными об округе, задачах и представителях.
- [x] Поле округа при регистрации переработано из `<input>` в `<select>` с данными из API.
```

## 3. Ссылки на YouGile

Список задач, которые закрывает PR. Порядок ссылок соответствует порядку пунктов в **Описании**.

```markdown
## Ссылки на YouGile
[MO-87](https://ru.yougile.com/team/5dce464829ca/#MO-87)
[MO-88](https://ru.yougile.com/team/5dce464829ca/#MO-88)
```

> Количество ссылок = количество пунктов в Описании. Если нет задач — PR не открывается.

---

## 4. Скриншоты изменений

Прикладывайте скриншоты для всех видимых изменений. Разделяйте их горизонтальной линией `---`.

```markdown
## Скриншоты изменений
<img width="1022" height="473" alt="Краткое описание" src="https://github.com/user-attachments/assets/..." />
---
<img width="378" height="530" alt="Краткое описание" src="https://github.com/user-attachments/assets/..." />
```

- Изображения загружаются через GitHub: перетащите файл в поле описания PR.
- Всегда заполняйте `alt` — что именно показано на скриншоте.
- Для backend-only изменений — скриншот из Swagger или Postman/Insomnia.
- Если визуальных изменений нет — напишите `_Визуальных изменений нет._`

---

## 5. Дополнительно

Опциональный раздел. Добавляйте, если есть важная информация **не привязанная к конкретной задаче**, но влияющая на ревью или деплой.

```markdown
## Дополнительно
- Обновлён `.env.example`: добавлена переменная `BALANCE_INITIAL_AMOUNT`.
- После мержа необходимо выполнить `npx prisma migrate deploy` на стейдже.
- Временно отключена валидация поля `district` до появления справочника округов (MO-110).
```

### Что сюда пишут:

- Изменения в конфигурации или переменных окружения, о которых нужно предупредить.
- Необходимые ручные действия после мержа (миграции, перезапуск сервисов).
- Временные решения (workaround) и технический долг, не оформленный задачей.
- Зависимости от других PR или веток.
- Вопросы к ревьюеру по архитектурным решениям.

> Если раздел не нужен — просто не добавляйте его.

---

## Чек-лист перед публикацией

- [ ] Тип указан корректно.
- [ ] Количество пунктов в Описании совпадает с количеством задач YouGile.
- [ ] Формулировки конкретны: нет расплывчатых «улучшен», «переработан» без деталей.
- [ ] Скриншоты приложены или явно указано, что их нет.
- [ ] Ветка актуальна (влита `main`/`develop`).
- [ ] Нет лишних файлов (`.env`, `node_modules`, логи).
- [ ] Код прошёл линтер (`eslint`, `prettier`).
- [ ] Раздел **Дополнительно** заполнен, если есть что сообщить ревьюеру.
