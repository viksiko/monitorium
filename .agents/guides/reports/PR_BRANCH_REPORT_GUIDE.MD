# 📎 Руководство по составлению приложения к Pull Request

Этот документ описывает стандарт составления **технического приложения к PR** — отдельного отчёта по ветке, который прилагается к основному PR-описанию и содержит контекст для ревьюера.

## Используемые гайды

| Гайд | Описание |
|------|----------|
| [GIT_GUIDE.MD](../git/GIT_GUIDE.MD) | Просмотр изменений ветки через git |

---

## Зачем нужно приложение

PR-описание в GitHub — это краткая сводка для команды. Приложение — это технический контекст для ревьюера: что именно было сделано внутри ветки, какие файлы затронуты, как устроено изменение. Особенно полезно для объёмных PR, где без контекста сложно понять логику изменений.

---

## Структура приложения

```
# Отчёт по ветке `<имя ветки>`

**Задача YouGile:** ссылка и краткое название задачи

---

## Заголовок Pull Request

<одна строка — текст для поля Title PR на GitHub>

---

## Краткая сводка
## Ключевые коммиты
## Backend
## Frontend
```

> Разделы **Backend** и **Frontend** добавляются только если соответствующие изменения есть. Для backend-only или frontend-only PR достаточно одного раздела.

> В файле `<имя-ветки>_branch.md` в разделе **Заголовок Pull Request** указывается **только** строка заголовка (см. ниже в этом гайде). Текст правил туда **не** копируют.

---

## Как собрать данные для приложения

Для получения данных об изменениях ветки используй **[GIT_GUIDE.MD](../git/GIT_GUIDE.MD)**.

Минимальный набор для составления приложения:
- Список коммитов — `git log <base>..<feature> --oneline` → раздел **Ключевые коммиты**
- Статистика файлов — `git diff <base>...<feature> --stat` → разделы **Backend** и **Frontend**

По умолчанию базовая ветка — `dev`. Полный порядок, синтаксис и примеры команд — в GIT_GUIDE.

## Описание разделов

### Заголовок и задача

```markdown
# Отчёт по ветке `feat/comments`

**Задача YouGile:** [MO-100](https://ru.yougile.com/team/5dce464829ca/#MO-100) — возможность оставлять комментарии к задачам и постам.
```

Укажите точное имя ветки и привяжите задачу из YouGile с коротким описанием.

---

### Заголовок Pull Request

Размещается **в приложении к PR** (`<имя-ветки>_branch.md`) **перед** разделом «Краткая сводка», сразу после блока с задачей YouGile и разделителя `---`.

**Назначение:** одна строка — предлагаемый **заголовок** будущего Pull Request (поле Title на GitHub или в аналоге). Формулируйте по сути изменений и при необходимости укажите ключи задач YouGile.

**Важно:** этот заголовок **не** переносите в файл основного PR-отчёта (`<имя-ветки>_pr.md`). В `_pr.md` остаётся только структура из `PR_REPORT_GUIDE.md` (тип, описание, ссылки, скриншоты, дополнительно), чтобы название PR не дублировалось в теле описания.

**В самом файле отчёта по ветке** под заголовком `## Заголовок Pull Request` пишите **только** эту строку — без пояснений «правило», «куда вставлять» и т.п. Всё такое излагается **только** в этом руководстве (`PR_BRANCH_REPORT_GUIDE.md`), а не в `_branch.md`.

Пример содержимого в `_branch.md`:

```markdown
## Заголовок Pull Request

MO-12, MO-34 — краткая суть изменений одной строкой
```

### Краткая сводка

Два-четыре предложения о том, что было сделано в ветке в целом. Пишите по существу: что реализовано, какие слои затронуты, есть ли нестандартные решения, которые нужно знать ревьюеру.

```markdown
## Краткая сводка

Реализованы комментарии к постам и задачам: БД, API, UI. Запросы с фронтенда строятся через типизированный HTTP-клиент (`comment.client.ts`) и React Query (`comment.query.ts`).
```

Не пересказывайте коммиты — это для следующего раздела. Здесь — только общая картина.

---

### Ключевые коммиты

Таблица коммитов в хронологическом порядке (от старых к новым). Группируйте близкие по смыслу коммиты в одну строку, если их много.

```markdown
## Ключевые коммиты

| Хэш | Описание |
|-----|----------|
| `4c37c63` | Модель Prisma, модуль, DTO, сервис, контроллер |
| `a2e0926` | Удалён сторонний генератор, добавлен свой |
| `c7c8aa3` … `d28987a` | UI комментариев для постов и задач |
```

Хэши берите из вывода `git log`. Достаточно первых 7 символов.

---

### Backend

Описывайте только то, что реально есть в проекте. Перечисляйте конкретные модули, сервисы, контроллеры, модели Prisma, эндпоинты.

```markdown
## Backend

- Добавлен `CommentModule` с сервисом и контроллером под `JwtAuthGuard`.
- Эндпоинты: `POST /api/v1/comments`, `GET /api/v1/comments`, `PATCH`, `DELETE`.
- Prisma: модель `Comment`, связи с `Post` и `Task`, каскадное удаление.
```

Не используйте термины, которых нет в проекте. Если в проекте нет очередей, gateway'ев или event-шины — не упоминайте их. Описывайте то, что сделано: модули, модели, эндпоинты.

---

### Frontend

Перечисляйте компоненты, страницы, хуки, файлы с запросами. Описывайте, куда подключены изменения.

```markdown
## Frontend

- Компоненты: `CommentsSection`, `CommentComponent`, `CommentsSectionForm`.
- Страницы `PostDetails` и `TaskDetails` подключены к комментариям.
- `comment.query.ts`: хуки `useGetComments`, `useCreateComment`, инвалидация кеша.
```

## Чек-лист перед публикацией приложения

- [ ] Имя ветки и ссылка на задачу YouGile указаны верно.
- [ ] Перед «Краткой сводкой» есть раздел **Заголовок Pull Request** с **одной** строкой текста для Title (без текста правил из гайда); эта строка **не** продублирована в `<имя-ветки>_pr.md`.
- [ ] Краткая сводка отражает суть изменений, а не пересказывает коммиты.
- [ ] Коммиты перечислены в хронологическом порядке, хэши корректны.
- [ ] В разделах Backend / Frontend упомянуты только реальные сущности проекта.
- [ ] Нет терминов, которые не используются в проекте.
